# Orch-lite

**让 Agent 去工作，让人继续交流。**

Orch-lite 是一个让 Coding Agent 支持后台执行的轻量级 Skill：把真正的活儿从当前会话里摘出去，派给后台 Agent 干，让等待时间大幅缩短，而不是把对话从头堵到尾。

它解决的是一个非常基础的人机交互问题——**Agent 工作时，人不应被迫干等。**

---

## 两种交互方式：串行，与解耦

### 传统的串行流程

传统的 Coding Agent 会话是一个串行循环：

```
你发需求
   ↓
Agent 开始工作
   ↓
你只能等
   ↓
Agent 做完
   ↓
你继续发下一个需求
```

这句话看着自然，但隐藏着一个假设：**你的工作节奏，被 Agent 的执行时间绑架了。** 任务越复杂、Agent 干得越久，你卡在对话前的等待就越长。而现实里，Agent 干活的中途你已经想到了下一个需求、发现了一个问题、或者只是想追问一句——但对话窗口是忙的，你只能等。

**等待的不是 Agent，是你。**

### 装 orch-lite 之后

Orch-lite 把"执行"和"对话"解耦，让两边各自拥有连续的时间线：

```
人的时间线：  请求A → 继续聊天 → 请求B → 查看A → 查看B → 请求C …
                    ↓           ↓            ↓
Agent 时间线：    执行A ──────→ 执行B ──────→ 执行C ──────→
```

- **人的决策流程保持连续**：你按自己的节奏，正常说话、提问、发新需求。
- **Agent 的执行可以并行推进**：某个任务完成后，它进入下一阶段继续跑，不等你这一下就停摆。

举例——假设你正在和 Agent 一起写一份报告（比如 Word 文档）：

```
10:00  你说：起草这份策划案的正文                      → Agent 开始后台写正文
10:03  你想到一个点子：加一段"竞品分析"                → Agent 接着写，记下这个新要求
10:06  你又说：竞品那段放最后，先把总结提上来          → Agent 继续调整
10:10  正文写完，Agent 把"竞品分析"也补上了            → 你查看，顺着思路往下一段走
```

这些新想法——加一段、换个顺序、改个思路——**都是在你写文档的连贯流程里自然冒出来的**。普通模式下，你得等正文写完才能再提一个；而在这里，你的思路一路往前走，Agent 在旁边把每一条接住、落实。**你的工作流是连续的，没有因为 Agent 正在赶稿就被卡住**（另开一个对话去并行做，反而会分散注意力、信息难互通、冲突难解决）。

要诚实说一点：**等待并没有消失，只是被大幅压缩**。当主会话自己需要做某些事——比如去搜索、去外部查证——对话同样要停下来。Orch-lite 减少的是"等待"这部分时间，而不是把它清零。

## 和当前多 Agent 方案差在哪里

你可能已经在别处见过"多 Agent 并行""后台执行""worktree"这些字眼。它们和 Orch-lite 的差别，不在技术，在**交互重心**：

| 维度 | 主流多 Agent 方案 | Orch-lite |
|---|---|---|
| 核心问题 | 让更多 Agent 一起工作、如何调度它们 | Agent 工作时，人为什么必须等 |
| 用户角色 | 容易变成盯着 A/B/C 跑到哪的"调度者" | 不做 Agent 管理员，只继续自己的工作 |
| 并行的是 | 任务的执行 | Agent 的执行，而不是你的决策流程 |
| 决策权 | 常被抽走、中间过程不可见 | 始终在人手里，时机不被执行的卡点绑架 |

一句话：**别人的重心在"让 Agent 更自主、更会并行"，Orch-lite 的重心在"让人的工作流不被打断"。** 底层你看到的那些能力——后台 Agent、worktree、任务隔离——Orch-lite 都会用到，但只是实现手段，不是它想成为的样子。

## 设计哲学：以人为中心

- **决策权交给人**。关键节点的方向始终由人把握——只是把握的时机不再被 Agent 的执行卡住：Agent 执行期间，你在任何时刻插入的问题、想法、纠正，都会触发主会话重新做一次方向判断；Agent 交付后，由你决定是否整合、如何整合。
  > 减少的，是等待；不是人。
- **高效率和自主性不该以吞掉人的决策为代价**。很多多智能体方案能展示"高效率"，却把人的决策过程抽走、隐藏掉——中间发生了什么、为什么这么拆、哪些决定是人做的，用户并不一定看得到。
- **Multi-Agent 是手段，不是目的**。它**不是**一个多 Agent 研究平台、Agent swarm、无人干预的长时自主系统、或通用分布式调度器。真正的问题是：**"Agent 工作的时候，为什么人必须等？"**

> Orch-lite 不是试图把人从工作流中移除，而是试图把**不必要的等待**从工作流中移除。

---

## 它怎么做到：机制与各自解决的问题

一句话版：**主会话只协调，具体工作派给后台子 Agent，状态和隔离落盘。**

| 机制 | 要解决的问题 |
|---|---|
| 主会话（Main Agent） | 每个请求先做一次"聊天 / 派发 / 并行协调"的方向判断；需要人拍板时把决定权交还 |
| 后台子 Agent | 真正执行文件修改、测试、调试等具体工作，让主会话保持轻 |
| 任务状态 / index | 脱离当前会话的工作仍然存在、可追踪，不受会话结束影响 |
| Git / worktree | 给并行任务明确的工作边界，互不污染，支持之后的整合 |

**派发即返回**：主会话把活儿派出去就结束这一轮，对话回到你手里；你继续说话，后台在悄悄推进。

请求据此走一个简单路由：**chat**（纯交流、阅读、分析）、**task**（派一个子 Agent 做明确的后台工作）、**orchestration**（已有后台任务在跑或有多项独立工作时开启并行协调）。

## 什么时候用

**适合**：需要改代码 / 改文件 / 跑较长时间的任务（重构、实现、生成测试、调试、写文档），有多个彼此独立的工作项，特别是当你**希望继续和 Agent 对话**的时候。

**不适合**：简单问答（如"Python 的 list 和 tuple 有什么区别"）、几秒就能完成的微小改动、存在严格先后依赖必须串行的强耦合工作。Orch-lite 不是"能并行就并行"，只有当并行能真正解除人的等待时才值得用。

---

## 也许并不适合你

- 并行任务之间存在文件冲突的可能，并行不代表一切都能安全并行；
- 等待被压缩而非消除——某些要主会话亲自跑的步骤（如搜索）仍会等待；
- 人的决策仍可能是实际瓶颈；
- 状态管理带来一定复杂度；
- 不是所有类型的任务都适合这种工作方式。
