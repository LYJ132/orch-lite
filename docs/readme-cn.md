# Orch-lite

**让 Agent 去工作，让人继续交流。**

Orch-lite 是一个让 Coding Agent 支持后台执行的轻量级 Skill：把真正的活儿从当前会话里摘出去，派给后台 Agent 干，让等待时间大幅缩短，而不是把对话从头堵到尾。

它解决的是一个非常基础的人机交互问题——**Agent 工作时，人不应该被迫干等。**

---

## 传统会话为什么阻塞人

传统的 Coding Agent 会话是一个串行循环：

```
你发需求
   ↓
Agent 开始工作
   ↓
你只能等
   ↓
Agent 做完
   ↓
你继续发下一个需求
```

这句话看着自然，但隐藏着一个假设：**你的工作节奏，被 Agent 的执行时间绑架了。**

任务越复杂，Agent 干得越久，你卡在对话前的等待就越长。而现实里，Agent 干活的中途你已经想到了下一个需求、发现了一个问题、或者只是想追问一句——但对话窗口是忙的，你只能等。

**等待的不是 Agent，是你。**

## Orch-lite 的做法：人不被堵住

Orch-lite 把"执行"和"对话"解耦，让两边各自拥有连续的时间线：

```
人的时间线：  请求A → 继续聊天 → 请求B → 查看A → 查看B → 请求C …
                    ↓           ↓            ↓
Agent 时间线：    执行A ──────→ 执行B ──────→ 执行C ──────→
```

- **人的决策流程保持连续**：你按自己的节奏，正常说话、提问、发新需求。
- **Agent 的执行可以并行推进**：某个任务完成后，它进入下一阶段继续跑，不等你这一下就停摆。

这里要诚实说清楚：**等待并没有消失，只是被大幅压缩**。当主会话自己需要做一些事情——比如要去搜索、要去外部查证——对话同样会停下来等它。Orch-lite 减少的是"等待"这部分时间，而不是把它清零。人说话、Agent 做事，彼此大部分时间不再互相堵住。

## 一个具体例子

假设你在和 Agent 一起改造登录模块：

```
10:00  你说：重构登录模块，改完我看一下          → Agent A 开始后台执行
10:02  你说：顺便帮我查一下数据库查询性能        → Agent B 开始执行
10:10  A 完成，你可以看它的改动并给出判断
10:12  你处理完 A，B 也已经做完了，直接进入 B
```

传统模式下，你得等 A 搞定、处理完、再让 B 开工、再等 B。在这里，A 和 B 在后台并行推进，而你只是顺着自己的节奏一路处理过来——**多出来的时间，就是等待被压缩掉的那部分。**

## 每条消息，人都在同时接收和发出

在 Orch-lite 里，"审批"不是一个单独的动作——它和"提需求"是同一条消息的两面。

你发完第一条需求之后，后面的每一条会话，都同时带着两个属性：

- **对已完成 / 进行中工作的判断、指导、纠正** —— 对 Agent 产出的回应；
- **对下一步方向的引导** —— 也就是一个新的需求。

人既是接收方，也是发出方。所以当 Agent 完成上一步、需要一个方向时，方向往往在你发出上一条消息时就已经聊定了——主会话也已经有了大致的方向。**决策不需要等 Agent 完成才做，它在路上就已经做出来了。**

## 和其他方式有什么不一样

你可能已经在别的产品里见过类似的字眼——"后台任务""多 Agent 并行"。它们和 Orch-lite 的差别在哪里？

- **Codex 的引导消息（lead/引导消息）**：这些产品会推送一条"引导消息"告诉你接下来可以做什么，本质上是**产品在引导你去提出问题**，主循环仍然是把一串串任务串起来的。Orch-lite 不同——它不主张由产品替你编排下一步，而是让你自己端着连续的工作流往前走，Agent 在旁边把你要的活儿同时做着。
- **一般的 Multi-Agent 编排**：主流多 Agent 产品的叙事往往围绕"让更多 Agent 一起工作、如何调度它们"展开，用户容易被迫变成一个**管理一堆并行 Agent 的调度者**——盯着 A 到哪了、B 到哪了、C 失败没有。Orch-lite 的取向相反：**并行的是 Agent 的执行，而不是你的决策流程**。你不去管理 Agent，你只是继续自己的工作，走到决策点时，后台已经把手上的阶段准备好了。

一句话概括差别：**别人的重心在"让 Agent 更自主 / 更会并行"，Orch-lite 的重心在"让人的工作流不被打断"。**

> 顺带一提，如果你看过 ChatGPT 之类的聊天里提到的"多 Agent 并行、后台执行、worktree"等概念，Orch-lite 用到的正是这些底层能力——但把它组织成一个明确的人机协作方式，而不是把它本身当作卖点。

## 它给你带来什么

三个收益：

1. **省时间**。你发出新请求时，上一个任务往往刚刚做完，决策已经在路上聊定；需要等的只剩少数真正要主会话亲自跑的步骤。等待大幅减少。
2. **会话更整洁**。具体操作被挂到后台去做，主对话不被执行流水刷屏，始终保持清爽的讨论氛围。
3. **省 token**。后台子 Agent 的执行开销移出主会话上下文，主会话只保留协调层，上下文更省、更聚焦。

## 人的控制权没有丢失

Orch-lite 不是为了把决定权交给 Agent。

它不是"让 Agent 自己把一切做完"。恰恰相反，关键节点的方向仍然由人把握——只是**把握的时机不再被 Agent 的执行卡住**。

- Agent 执行期间，你在任何时刻插入的问题、想法、纠正，都会触发主会话重新做一次方向判断；
- Agent 交付结果后，由你对是否整合、如何整合做决定。

> 减少的，是等待；不是人。

## Multi-Agent 是手段，不是目的

Orch-lite 会用一个或多个后台 Agent，但那只是为了实现上面这套非阻塞体验的**技术手段**，不是产品本身。

它**不是**：

- 一个多 Agent 研究平台
- 一个无限派生的 Agent swarm
- 一个无人干预、长时自主运行的系统
- 一个通用的分布式任务调度器

真正的问题是：**"Agent 工作的时候，为什么人必须等？"** 后台 Agent、任务状态、Git 隔离——都是为了回答这个问题而存在的设施。

## 它怎么做到

一句话版：**主会话只协调，具体工作派给后台子 Agent，状态和隔离落盘。**

| 机制 | 作用 |
|---|---|
| 主会话（Main Agent） | 理解请求、判断是否后台执行、派发任务、协调状态、在需要人拍板时把决定权交还 |
| 后台子 Agent | 真正执行文件修改、测试、调试等具体工作 |
| 任务状态 / index | 让脱离当前会话的工作仍然存在、可追踪，不受会话结束影响 |
| Git / worktree | 给并行任务明确的工作边界，互不污染，支持之后的整合 |

**派发即返回**：主会话把活儿派出去就结束这一轮，对话回到你手里；你继续说话，后台在悄悄推进。

## 请求如何被处理

为了实现上述工作方式，请求会走一个简单的路由：

- **chat** —— 纯交流、阅读、分析，不需要后台任务；
- **task** —— 一个明确的后台工作，派一个子 Agent 去执行；
- **orchestration** —— 已有后台任务在跑、新工作到来，或有多个彼此独立的工作项时，开启并行协调。

这只是支撑"非阻塞工作流"的路由方式，不是产品卖点本身。

## 什么时候用

**适合**：需要改代码 / 改文件 / 跑较长时间的任务（重构、实现、生成测试、调试、写文档），或者有多个彼此独立的工作项，特别是当你**希望继续和 Agent 对话**的时候。

**不适合**：简单问答（如"Python 的 list 和 tuple 有什么区别"）、几秒就能完成的微小改动、以及存在严格先后依赖、必须串行的强耦合工作。Orch-lite 不是"能并行就并行"，只有当并行能真正解除人的等待时才值得用。

## 支持的环境与安装

- **Claude Code / ZCode**：完整支持，hook 自动注册。
- **Codex**：需手动信任 hook；未信任时退化为纯模型纪律模式，依然安全。

安装方式见下文链接；更详细部署规则见 `docs/maintenance.md`。

## 它不是万能模型

如实说明边界：

- 并行任务之间存在文件冲突的可能；并行不意味着一切都能安全并行；
- 等待被压缩而非消除——某些主会话要亲自跑的步骤（如搜索、外部查证）仍会等待；
- 人的决策仍可能是实际瓶颈；
- 状态管理带来一定的复杂度；
- 不是所有类型的任务都适合这种工作方式。

## 为什么这样一个人机关系值得坚持

现在很多多智能体方案，能展示"高效率"，但往往把人的决策过程从中抽走、隐藏掉，中间发生了什么、为什么这么拆、哪些决定是人做的，用户并不一定看得到。

Orch-lite 反过来的取舍是——**用机器侧的并行去服务人的连续工作流，而不是用多 Agent 去替代人的决策**。

> Orch-lite 不是试图把人从工作流中移除，而是试图把**不必要的等待**从工作流中移除。
