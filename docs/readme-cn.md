# Orch-lite

**让 Agent 去工作，让人的工作流继续。**

Orch-lite 是一个面向 Coding Agent 的轻量级后台执行 Skill。

它做的事情很简单：**把 Agent 的执行与人的对话和决策解耦。**

当 Agent 需要修改代码、运行测试、调试、生成文档等较长时间的工作时，不必占住当前会话等待执行结束，而是把具体工作交给后台 Agent。

与此同时，人可以继续思考、提问、补充需求、调整方向，甚至开始下一个任务。

Agent 在工作，人也继续工作。

---

## 它真正解决的问题

传统的 Coding Agent 往往是一个串行的交互过程：

```
人提出需求
    ↓
Agent 开始执行
    ↓
人等待 Agent
    ↓
Agent 执行完成
    ↓
人查看结果
    ↓
人提出下一个需求
```

看起来只是一个正常的对话流程，但这里实际上存在两个方向的阻塞。

### 1. 人在等 Agent

Agent 正在修改代码、运行测试、调试问题时，人通常只能等它完成。

但人的思考并不会停止。等待期间，你可能已经：

- 想到了新的需求；
- 发现了刚才方案的问题；
- 想继续追问一个概念；
- 想让 Agent 做另一件独立的事情；
- 想开始下一个任务。

然而当前 Agent 仍然处于执行状态。

**Agent 的执行时间，直接变成了人的等待时间。**

### 2. Agent 也在等人

另一个方向的问题恰恰相反。

Agent 在执行过程中经常需要：

- 等待人提供方向；
- 等待人回答问题；
- 等待人确认方案；
- 等待人决定下一步；
- 等待人审核结果。

于是传统流程实际上变成了：

```
人 → Agent → 人 → Agent → 人 → Agent
```

**人的决策与 Agent 的执行被强行绑定在同一条时间线上。**

这意味着：人必须等 Agent，Agent 也必须等人。而很多时候，这种等待并不是工作本身必须如此，只是当前交互方式造成的。

---

## 另一个被忽略的问题：长会话会被执行内容污染

Coding Agent 的一个典型会话可能越来越长：

```
用户需求 → Agent 分析 → 工具调用 → 代码修改 → 终端输出
   → 测试 → 报错 → 调试 → 再次修改 → 再次测试 → ...
```

这些内容对 Agent 完成当前任务可能很重要，却不一定是你长期交流时最重要的内容。

随着任务变长，主会话会逐渐堆积：

- 代码、diff；
- 日志、测试结果；
- 调试过程、工具调用；
- 临时错误、大量执行细节。

结果就是：**本来用于理解需求、想法和决策的会话，逐渐变成了 Agent 的执行日志。** 这不仅影响阅读体验，也让上下文越来越臃肿。

---

## Orch-lite：把两条时间线解耦

Orch-lite 的核心并不是简单地"增加几个 Agent"。

真正的变化是：**让人的工作流和 Agent 的执行拥有各自独立的时间线。**

![Orch-lite：两条时间线解耦](orch-lite.png)

上图是两种交互的对比：

- **上方（传统模式）**：Agent 的 Task A/B/C 与人的 Read & Send（阅读并发送）串行错开——任务在跑，人只能等；人发了话，Agent 才开始下一个，两边互相等待。
- **下方虚线框（Orch-lite）**：Task A/B/C 紧密排成连续的流水线，人的 Send、Read & Send 穿插在任务执行期间。Agent 持续推进，人也持续工作。

两条时间线不再完全同步。你的决策流程保持连续，Agent 的执行在后台并行推进。

**让 Agent 去工作，让人的工作流继续。**

---

## Orch-lite 的价值：三个层面的解耦

### 1. 工作流解耦

这是最核心的一层：Agent 执行任务时，人不需要停止自己的工作。

```
人的工作流：  ─────────────────────────────→
Agent A：     ──────────→
Agent B：          ─────────────→
Agent C：                 ───────────→
```

Agent 的执行时间不再直接等价于人的等待时间。

等待不会完全消失——某些工作本身仍需主会话执行，例如需要即时搜索、复杂讨论，或者等待人的决定。Orch-lite 做的是：**尽可能把原本不必要的等待移出人的工作流。**

### 2. 上下文解耦

执行任务所需的大量细节，不再全部堆积在主会话中。

```
主会话                      后台 Agent
├── 用户需求                ├── 文件修改
├── 想法                    ├── 工具调用
├── 方向                    ├── 测试
├── 问题                    ├── 日志
├── 决策                    ├── Debug
└── 审核结果                └── 执行细节
```

主会话因此保持相对整洁。执行细节仍然存在，也仍然可以被任务系统追踪，但不必持续占据人与 Agent 交流的主要空间。

这也意味着：主会话上下文更干净、不必要的执行内容更少、长会话更容易维持，并且在适当场景下可以减少上下文的 Token 消耗——Token 节省是这种上下文解耦带来的结果，而不是唯一目标。

### 3. 注意力与认知解耦

主会话真正重要的内容应该是：

- 我想做什么？
- 为什么这么做？
- 方向是什么？
- 有哪些问题？
- 我要怎么选择？
- 下一步应该做什么？

而不是：

- Agent 刚刚执行了什么？
- 这个命令输出了什么？
- 这个测试为什么失败？
- 这个文件第 237 行发生了什么？

后者对执行任务很重要，但不该持续占据主要交流空间。**主会话应该是用户与 Agent 思考的空间，而不是 Agent 的执行日志。** 当主会话更聚焦于需求、理念、方向和决策时，Agent 也能把更多注意力放在理解用户真正想做什么上，而不是在大量执行细节中消耗上下文。

---

## 人仍然掌握着决策权

解耦执行与交互，不意味着把人从工作流中移除。

Orch-lite 的目标不是"让 Agent 自己决定一切"，而是：**机器可以并行工作，但重要的决策仍然由人掌握。**

```
Agent 执行 → 发现需要方向判断 → 交还给人 → 人做决定 → Agent 继续执行
```

或者：

```
Agent A 执行中、Agent B 执行中
   → A 完成 → 人审核 A → 人决定是否继续 / 修改 / 整合
```

人的决策流程仍然存在。改变的是：**人不再需要为了等待 Agent 完成而暂停自己的工作。**

所以 Orch-lite 的原则是：**减少的是等待，不是人。**

---

## Multi-Agent 是手段，不是目的

Orch-lite 使用后台 Agent、任务状态、Git、worktree 等机制，是因为它们能帮助实现上述目标。但它本身并不是为了：

- 创建 Agent swarm；
- 让大量 Agent 自主协作；
- 建立通用分布式调度系统；
- 追求 Agent 数量；
- 让 Agent 尽可能长时间自主运行。

它关注的是另一个问题：**为什么 Agent 工作的时候，人必须停止自己的工作？**

因此：Multi-Agent 是实现手段，而不是产品目标。

---

## 它和一般的 Multi-Agent 有什么不同

你可能已经见过 Multi-Agent、Parallel Agents、Background Agents、Worktree、Agent Orchestration 这些概念，它们并不是 Orch-lite 独有的。区别在于交互重心：典型方案关心如何让更多 Agent 协作，而 Orch-lite 关心如何让人的工作流不被 Agent 阻塞。

所以 Orch-lite 说的不是"我们比别人有更多 Agent"，而是：**Agent 的工作，不应该成为人的工作流的阻塞点。**

---

## 它怎么做到

Orch-lite 用几个相对简单的机制实现这种交互方式。

### 主会话：负责协调，而不是承担所有执行

主 Agent 主要负责：

- 理解用户当前意图；
- 判断这是聊天还是实际工作；
- 判断是否需要后台执行；
- 分派任务；
- 协调正在执行的任务；
- 在需要时向用户请求决策；
- 根据任务结果继续推进工作流。

主会话尽量避免承担大量具体的文件修改和长时间执行。

### 后台子 Agent：负责真正干活

具体任务交给后台子 Agent：修改代码、改文件、重构、写测试、跑测试、Debug、生成文档，以及其他适合后台执行的工作。

```
Main Agent
   ├── Task A → Background Agent
   ├── Task B → Background Agent
   └── Task C → Background Agent
```

主会话可以立即回到与用户的交流中。

### 任务状态：让后台工作脱离当前会话仍然存在

后台任务不能只存在于某一次对话上下文里。因此 Orch-lite 使用持久化任务状态记录：

```
Task
 ├── task_id
 ├── status
 ├── objective
 ├── acceptance criteria
 ├── agent
 ├── branch / worktree
 └── result
```

即使主会话继续处理其他事情，之前派出的任务仍然可以被追踪。

### Git / Worktree：隔离并行任务

多个后台任务同时修改代码时，需要有明确的工作边界。Orch-lite 用 Git branch / worktree 对并行工作做隔离：

```
          Repository
   ┌──────────┼──────────┐
   ↓          ↓          ↓
 Task A     Task B     Task C
 worktree   worktree   worktree
   │          │          │
   ↓          ↓          ↓
 Agent A    Agent B    Agent C
```

这样可以减少不同 Agent 之间互相污染工作区的风险，并为后续整合提供基础。

## 派发即返回

Orch-lite 的一个重要交互原则是：**任务派出去以后，主会话尽快回到用户手里。**

```
传统：  用户 → Agent 执行 → 等待 → 执行完成 → 继续交流

Orch-lite：
  用户
   ↓
Main Agent → 派发任务 → 立即返回 → 继续交流
                  ↘ Background Agent → 执行任务 → 完成 / 等待决策
```

这样，后台执行不会天然占住主会话。

---

## 一个简单的任务路由

Orch-lite 把请求大致分成三类：

**chat** —— 纯交流、阅读、分析、解释等：

```
用户 → Main Agent → 直接处理
```

**task** —— 存在一个明确、适合后台执行的工作：

```
用户 → Main Agent → Background Agent → 执行任务
```

**orchestration** —— 已有后台任务，或当前请求包含多个可独立执行的工作项：

```
              Main Agent
             /    |    \
        Task A  Task B  Task C
         ↓       ↓       ↓
      Agent A  Agent B  Agent C
```

这里的 orchestration 不是为了建立复杂的调度平台，而是为了保证多个后台任务能在人的连续工作流中被安全地管理。

## 任务生命周期

一个后台任务大致经历：

```
NEW → DISPATCHED → RUNNING → COMPLETED → REVIEW / INTEGRATE
                        │
                        ├─→ HELP_REQUEST → 人做决策 → RUNNING
```

任务的具体状态和协议由 Orch-lite 的状态与协议文件定义。

---

## 并行并不意味着"能并行就并行"

Orch-lite 不鼓励无意义的并发。如果两个任务：

- 修改同一个文件；
- 强依赖前一个任务的结果；
- 必须严格按照顺序执行；
- 并行会导致复杂的冲突处理；

那么强行并行反而会降低效率。

真正值得并行的是：**并行能解除人的等待，并且不破坏任务之间的正确性。**

所以：并行是一种手段，而不是 KPI。

---

## 什么时候适合使用

Orch-lite 特别适合：

- 较长时间的代码修改、重构、Debug、文档生成；
- 编写测试、可后台运行的检查任务；
- 多个独立功能的开发；
- 用户希望在 Agent 工作时继续交流的场景。

尤其适合这种情况：**"这个任务让 Agent 慢慢做，但我还有别的事情想和 Agent 讨论。"**

---

## 什么时候不适合

- **简单问答**：例如"Python 的 list 和 tuple 有什么区别"，没必要启动后台 Agent。
- **极短任务**：几秒就能完成的修改，后台调度本身可能比直接执行更复杂。
- **强耦合任务**：任务 B 必须等待任务 A 的结果时，并行没有意义。
- **无法安全隔离的任务**：多个任务必须同时修改同一个资源、容易产生冲突时，需要谨慎使用并行。

---

## 当前的限制

Orch-lite 并不会让所有等待消失。目前仍有一些限制：

- 人的决策本身可能成为瓶颈；
- 某些工作必须由主会话完成；
- 外部搜索、查证等操作仍可能产生等待；
- 并行任务之间仍可能产生资源冲突；
- Git / worktree 会增加一定复杂度；
- 后台任务需要额外的状态管理；
- 不同 Coding Agent 对后台执行、Hook 和生命周期的支持程度不同。

因此 Orch-lite 的目标不是"零等待"，而是：**不要让本来可以并行的 Agent 执行阻塞人的工作流。**

## 核心设计原则

1. **对话和执行分离**。主会话与人类对话，负责理解、讨论和决策；后台 Agent 负责真正的代码、文件、测试、Debug 等执行工作。
2. **人的工作流不应该被 Agent 的执行时间绑架**。Agent 执行多久 ≠ 人等待多久，这是 Orch-lite 最核心的目标。
3. **主会话保持干净**。主会话聚焦需求、想法、方向、问题、决策、反馈，而不是代码、日志、工具调用、测试输出、Debug 过程。
4. **人的决策权不因并行而消失**。后台执行不是自动决策。Agent 可以提前工作，但重要的方向、审核和整合仍然回到人手里。
5. **Multi-Agent 是手段，不是目的**。如果任务不需要并行，就不应该为了"Multi-Agent"而使用 Multi-Agent。

---

## 最后

Orch-lite 并不试图让 Agent 取代人的工作。它想改变的是人与 Agent 一起工作的时间结构。

传统模式更像：

```
人 ──→ Agent
↑        │
└────────┘
   互相等待
```

Orch-lite 希望变成：

```
人的工作流 ─────────────────────────────→
Agent A   ─────────────→
Agent B        ─────────────→
Agent C             ────────────→
```

Agent 去工作，人继续思考、交流和做决定。

最终希望实现的不是"让人退出工作流"，而是**"让不必要的等待退出工作流"**。

让 Agent 去工作，让人的工作流继续。
